## 1. 개요 (Overview)



이 문서는 **prove-geo-web-app** 프로젝트의 기술적 방향성을 결정하는 최상위 원칙을 정의합니다. 모든 코드는 이 원칙을 기반으로 작성되어야 하며, 여기에 명시된 내용과 다른 접근 방식이 필요할 경우 반드시 팀의 기술 리더와 합의를 거쳐야 합니다.



이 원칙들은 `Next.js`의 서버 중심 패러다임과 `Supabase`의 강력한 BaaS(Backend-as-a-Service) 기능을 결합하여, **안정적이고 확장 가능하며 예측 가능한** 애플리케이션을 구축하는 것을 목표로 합니다.



---



## 2. 핵심 원칙 (Core Principles)



### 원칙 1: Supabase는 데이터베이스, Next.js는 서버 (Supabase for Database, Next.js for Server)



- **Supabase의 역할:** 우리 아키텍처에서 `Supabase`는 주로 **데이터 영속성 계층(Persistence Layer)**, 즉 **데이터베이스(`Postgres`)**와 **인증(`Authentication`)** 서비스의 역할을 수행합니다.

- **Next.js의 역할:** `Next.js`는 단순히 프론트엔드를 렌더링하는 도구를 넘어, **애플리케이션의 유일한 서버(Application Server)** 역할을 담당합니다. 모든 비즈니스 로직, 유효성 검사, 외부 API 연동 등은 `Next.js`의 서버 환경(서버 컴포넌트, 서버 액션, API 라우트) 내에서 처리됩니다.

- **🚫 Supabase Edge Functions 금지:** 프로젝트의 복잡성을 낮추고 코드의 응집도를 높이기 위해, 별도의 백엔드 로직을 위한 `Supabase Edge Functions`는 **절대 사용하지 않습니다.**



### 원칙 2: 데이터 처리는 RLS로 보호된 범위 내에서 허용 (RLS-Protected Data Handling)



- **데이터 조회(Fetching):**



- **기본:** 데이터 조회는 **`서버 컴포넌트`**에서 Supabase 서버 클라이언트(`lib/supabase/server.ts`)를 통해 직접 수행하는 것을 **기본 원칙**으로 합니다. 이는 클라이언트에 민감한 로직 노출을 막고, 렌더링 성능을 최적화하는 가장 효과적인 방법입니다.

- **RLS 존중:** 일반적인 데이터 조회는 `ANON_KEY`를 사용하는 서버 클라이언트를 통해 수행하며, 이는 Row Level Security(RLS) 정책을 존중합니다. 사용자 세션 정보는 쿠키를 통해 자동으로 전달됩니다.



- **데이터 변경(Mutation):**

- **RLS로 보호된 직접 쓰기 허용:** 가장 낮은 레벨의 유저는 **RLS 정책으로 보호된 범위 내에서 자신의 데이터에 대해서만** 클라이언트에서 직접 읽기, 쓰기, 수정을 수행할 수 있습니다. 이는 성능 최적화와 서버 부하 분산을 위한 핵심 전략입니다.

- **RLS 정책의 역할:** RLS 정책은 사용자가 자신의 데이터(`auth.uid() = user_id`)에 대해서만 접근할 수 있도록 엄격하게 제한해야 합니다. 이를 통해 클라이언트에서 직접 쓰기를 허용하더라도 보안이 보장됩니다.

- **서버 액션의 역할:** 복잡한 비즈니스 로직, 크로스 유저 작업, 또는 추가 검증이 필요한 경우에만 `Next.js 서버 액션`을 사용합니다. 예를 들어:

- 여러 테이블에 걸친 트랜잭션 작업

- 다른 사용자의 데이터에 영향을 미치는 작업

- 복잡한 권한 검증이 필요한 작업

- 외부 API 연동이 필요한 작업

- **삭제는 없다, 오직 상태 변경만 있을 뿐 (Soft Deletes Only):** 모든 데이터의 '삭제'는 물리적 `DELETE`가 아닌, `status` 필드를 `'deleted'`로 변경하고 `deleted_at` 타임스탬프를 기록하는 **소프트 삭제(Soft Delete)** 방식으로만 수행해야 합니다. 이는 데이터 복구와 감사 추적을 용이하게 하는 핵심 안전장치입니다.



### 원칙 3: 보안은 계층적으로 (Defense in Depth)



우리 시스템의 보안은 두 개의 핵심 계층으로 구성됩니다.



1. **데이터베이스 계층 (in Supabase) - 1차 방어선:**



- **주요 관문:** `Row Level Security (RLS) 정책`이 모든 데이터 접근에 대한 **주요 관문(Primary Gatekeeper)** 역할을 합니다. RLS 정책은 사용자가 자신의 데이터(`auth.uid() = user_id`)에 대해서만 읽기, 쓰기, 수정을 허용하도록 엄격하게 제한합니다.

- **정책의 역할:** RLS 정책은 "이 사용자가 이 행의 소유자인가? (`auth.uid() = user_id`)"와 같이 데이터의 소유권을 검증하는 핵심 역할을 수행합니다. 이를 통해 클라이언트에서 직접 데이터를 조작하더라도 보안이 보장됩니다.



2. **애플리케이션 계층 (in Next.js) - 2차 방어선:**

- **복잡한 비즈니스 로직:** `서버 액션`은 복잡한 비즈니스 로직, 크로스 유저 작업, 또는 추가 검증이 필요한 경우에 사용됩니다. 서버 액션 내부에서 역할(Role) 기반 권한, 입력 데이터의 유효성, 트랜잭션 일관성을 철저히 검증합니다.

- **보완적 역할:** 서버 액션은 RLS 정책으로 보호할 수 없는 복잡한 비즈니스 규칙을 처리하는 보완적 역할을 수행합니다.



### 원칙 4: 상태는 서버에, UI 상태는 클라이언트에 (Server for State, UI State for Client)



- **데이터의 진실 공급원(SSoT):** 데이터의 유일하고 진실된 공급원은 **`Postgres 데이터베이스`** 입니다.

- **상태 중복 최소화:** 서버의 데이터를 클라이언트 상태 관리 라이브러리(`Zustand` 등)에 그대로 복제하여 사용하는 것을 **지양**합니다. 서버 데이터는 필요시 다시 조회하는 것을 원칙으로 합니다.

- **클라이언트 상태의 역할:** 클라이언트 상태 관리(`Zustand`)는 오직 **UI와 직접적으로 관련된, 비영속적인 상태**를 관리하기 위해서만 사용합니다.

- 예시: 모달의 열림/닫힘 상태, 폼 입력 값, 현재 로그인한 사용자 정보 객체 등



### 원칙 5: 코드는 예측 가능하게 (Predictable Code)



- **의존성 주입(DI):** 서버 사이드의 모든 서비스(예: `UserService`, `CompanyService`)는 필요시 `InversifyJS`를 통한 **의존성 주입 패턴**을 따라야 합니다. 이는 코드의 결합도를 낮추고, 테스트 용이성을 극대화하며, 로직의 흐름을 명확하게 만듭니다. 단, 프로젝트 규모와 복잡도에 따라 DI 없이 직접적인 서비스 호출도 허용됩니다.

- **엄격한 타입 시스템:** `TypeScript`를 프로젝트 전반에 걸쳐 적극적으로 사용합니다. 특히 Postgres 데이터베이스의 데이터 구조를 정의하는 `interface`/`type`은 중앙에서 관리하여 데이터의 일관성과 안정성을 보장해야 합니다.

- **가이드 준수:** 본 문서는 최상위 원칙을 다룹니다. 각 원칙의 구체적인 구현 방법과 모범 사례는 이어지는 아키텍처 가이드 문서들(`01`~`13`)에 상세히 기술되어 있으니 **반드시 숙지하고 준수해야 합니다.**

## 3. Supabase 클라이언트 사용 원칙



### 3.1. 서버 클라이언트 (`lib/supabase/server.ts`)



- **용도:** 서버 컴포넌트와 서버 액션에서 사용

- **키:** `PUBLISHABLE_KEY` 사용 (RLS 정책 존중)

- **특징:** 사용자 세션 정보는 쿠키를 통해 자동으로 전달됨

- **사용 예시:**

```typescript

const supabase = await createClient()

const { data } = await supabase.from('profiles').select()

```



### 3.2. Admin 클라이언트 (필요시)



- **용도:** RLS를 우회해야 하는 관리자 작업에만 사용

- **키:** `SERVICE_ROLE_KEY` 사용

- **주의:** 보안상 매우 제한적으로 사용해야 하며, 일반적인 데이터 조회/변경에는 사용하지 않음

- **위치:** `lib/supabase/admin.ts` (필요시 생성)



### 3.3. 브라우저 클라이언트 (`lib/supabase/client.ts`)



- **용도:** 클라이언트 컴포넌트에서 RLS로 보호된 자신의 데이터에 대한 직접 접근

- **키:** `PUBLISHABLE_KEY` 사용 (RLS 정책 존중)

- **사용 범위:**

- 자신의 데이터(`auth.uid() = user_id`)에 대한 읽기, 쓰기, 수정

- RLS 정책으로 엄격하게 보호된 범위 내에서만 사용

- **주의:** 다른 사용자의 데이터나 복잡한 비즈니스 로직이 필요한 경우에는 서버 액션을 사용해야 함

## 4. 데이터베이스 네이밍 컨벤션



- **테이블/컬럼명:** `snake_case` 사용 (Postgres 표준)

- **소프트 삭제 필드:** `deleted_at` (타임스탬프), `status` (상태 값)

- **타임스탬프 필드:** `created_at`, `updated_at`, `deleted_at` (모두 `timestamptz` 타입)

## 5. 결론



이 원칙들은 프로젝트의 기술적 방향성을 결정하는 핵심입니다. 모든 개발자는 이 원칙을 숙지하고, 코드 작성 시 이를 준수해야 합니다. 원칙을 위반해야 하는 특별한 경우가 있다면, 반드시 팀의 기술 리더와 논의한 후 진행해야 합니다.
