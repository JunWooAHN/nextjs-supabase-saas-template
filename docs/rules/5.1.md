# **\[1단계 계획 v5.6\] 빌링 & 구독 + 통합 접근 제어 (3-Tier 아키텍처 모델 반영)**

## **1\. 핵심 목표 및 사용자 역할**

SaaS의 핵심 사용자 역할을 정의합니다. (일반 사용자, 조직 매니저, 센터 오너, 법정 대리인, 앱 매니저 등)

1. **일반 사용자 (General User)**  
   * SPA와 같은 부드러운 UX.  
   * 조직(Organization)에 가입(안되어 있을 수 있음).  
   * 자신이 속한 조직의 데이터만 접근.  
2. **조직 매니저 (Organization Manager)**  
   * 조직 소유자와 거의 동일한 RLS 권한 (조직 관리).  
3. **조직 소유자 (Organization Owner)**  
   * 조직 설정, 멤버 관리, 데이터 관리.  
4. **센터 매니저 (Center Manager)**  
   * 센터 소유자와 거의 동일한 RLS 권한 (센터 관리).  
5. **센터 소유자 (Center Owner)**  
   * 센터 설정, 멤버(조직 소유자) 초대, 센터 데이터 관리.  
6. **법정 대리인 (Law Agency)**  
   * (v3.5) CENTER 엔티티이면서 CENTER\_IS\_LAW\_AGENCY 권한 비트를 가진 역할.  
7. **앱 매니저 (App Manager)**  
   * SaaS 플랫폼 전체(모든 사용자/조직) 관리.

## **2\. 전체 아키텍처 개요 (3-Tier 모델 반영)**

* **프론트엔드/백엔드:** Next.js (App Router)로 통일.  
* **데이터베이스/인증:** Supabase (Auth \+ Postgres DB \+ RLS)  
* **핵심 로직:** 비트 연산(Bitwise) 권한 시스템 및 2개의 엔티티 타입(integer) 사용.  
  * **비트 연산(Bitwise) 권한 시스템**을 기반으로 합니다.  
  * **엔티티 타입**은 integer 상수(1: ORGANIZATION, 2: CENTER)로 관리됩니다.  
  * **3-Tier 아키텍처 모델:**
    * **Tier 1 (일반 사용자)**: 'use client' 컴포넌트에서 Supabase 브라우저 클라이언트(PUBLISHABLE_KEY)를 통해 RLS(행 수준 보안) 정책으로 보호된 데이터에 직접 접근합니다. SPA와 같은 부드러운 UX를 제공합니다.
    * **Tier 2 (SaaS 관리자 - 조직/센터)**: tRPC 프로시저 내에서 Supabase 서버 클라이언트(PUBLISHABLE_KEY, RLS 적용)를 사용해 복잡한 비즈니스 로직(멤버 초대, 권한 변경, 빌링)을 타입-안전하게 처리합니다.
    * **Tier 3 (앱 매니저)**: Server Actions 내에서 Supabase 어드민 클라이언트(service_role 키)를 사용해 RLS를 우회하는 플랫폼 전체 관리를 수행합니다.

export const PERMISSIONS \= {

  ORG\_EDIT\_SETTINGS: 1n \<\< 1n,  
  ORG\_MANAGE\_MEMBERS: 1n \<\< 2n,   
  ORG\_VIEW\_PROJECTS: 1n \<\< 3n,  
  ORG\_EDIT\_PROJECTS: 1n \<\< 4n,

  // \--- 센터(Center) 권한 (Type: 2\) \---  
  CENTER\_VIEW: 1n \<\< 10n,  
  CENTER\_EDIT\_SETTINGS: 1n \<\< 11n,  
  CENTER\_MANAGE\_ORGS: 1n \<\< 12n,   
  CENTER\_IS\_LAW\_AGENCY: 1n \<\< 13n, 

  // \--- 앱 매니저 \---  
  IS\_APP\_MANAGER: 1n \<\< 60n,

// \--- 역할별 권한 프리셋 (Roles as Permission Sets) \---  
export const ROLES \= {

  CENTER\_OWNER: PERMISSIONS.CENTER\_MANAGER | (1n \<\< 14n),

## **5\. 데이터베이스 스키마 (Supabase) \- v5.2 수정**

**PostGIS 확장 사용**: 모든 위치 데이터는 PostGIS의 `GEOMETRY(Point, 4326)` 타입을 사용하여 공간 인덱스(GIST)로 반경 검색을 최적화합니다.

**마이그레이션 시작 시 PostGIS 확장 활성화:**
```sql
CREATE EXTENSION IF NOT EXISTS postgis;
```

결제 관련 3개 테이블과 위치 관련 2개 테이블이 **신규** 추가되었습니다.

1. **profiles (사용자 프로필)**  
   * id: uuid (auth.users.id와 동일. Primary Key)  
   * email: text  
   * full\_name: text  
   * permissions: bigint (기본값 0). (IS\_APP\_MANAGER 비트 체크용)  
   * created\_at: timestamp  
2. **centers (센터)**  
   * id: uuid (Primary Key, gen\_random\_uuid())  
   * name: text  
   * created\_at: timestamp  
3. **organizations (조직/테넌트)**  
   * id: uuid (Primary Key, gen\_random\_uuid())  
   * name: text  
   * created\_at: timestamp  
4. **memberships (핵심 멤버십 테이블)**  
   * user\_id: uuid (profiles.id 참조)  
   * entity\_id: uuid (organizations.id 또는 centers.id 참조)  
   * entity\_type: smallint (1=ORG, 2=CENTER)  
   * permissions: bigint (기본값 0).  
   * *Primary Key: (user\_id, entity\_id)*  
5. **center\_org\_relationships (N:M 센터-조직)**  
   * center\_id: uuid (centers.id 참조)  
   * organization\_id: uuid (organizations.id 참조)  
   * *Primary Key: (center\_id, organization\_id)*  
6. **projects (조직별 데이터 예시)**  
   * id: uuid  
   * name: text  
   * org\_id: uuid (organizations.id 참조).  
   * created\_at: timestamp  
7. **`location_proofs` (위치 증빙) \- v5.2 PostGIS 수정**  
   * `id`: `uuid` (Primary Key, `gen_random_uuid()`)  
   * `user_id`: `uuid` (profiles.id 참조)  
   * `entity_id`: `uuid` (`organizations.id` 또는 `centers.id` 참조)  
   * `entity_type`: `smallint` (1: ORGANIZATION, 2: CENTER)  
   * **`proof_category`: `smallint`** (v4.2) (1: 출근, 2: 퇴근, 3: 일반. `constants.ts` 참조)  
   * **`proof_method`: `smallint`** (v4.2 신규) (1: GPS, 2: QR, 3: INSTANT\_QR... `constants.ts` 참조)  
   * **`geom`: `geometry(Point, 4326)`** (v5.2 신규) PostGIS Point 타입 (WGS84 좌표계)  
   * `location`: `jsonb` (예: `{ "latitude": 37.123, "longitude": 127.123, "accuracy": 15.0 }`) - 호환성 유지 (deprecated)  
   * `created_at`: `timestamp with time zone` (기본값 `now()`)

## **5-1\. 위치 검증 로직 (v5.2 신규)**

**위치 검증 우선순위:**
1. **직원별 근무지 확인**: 해당 직원의 `member_work_locations` 중 활성 근무지의 반경 내인지 확인
2. **조직 기본 사업장 확인**: 조직의 `work_locations` 중 활성 사업장의 반경 내인지 확인
3. **아무데서나 허용**: 조직의 `work_locations.allow_anywhere = true`이면 위치 제한 없음

**PostGIS 위치 검증 쿼리 예시:**
```sql
-- 특정 위치가 직원 근무지 반경 내에 있는지 확인
SELECT 
  mwl.id,
  mwl.name,
  ST_Distance(
    mwl.geom::geography,
    ST_SetSRID(ST_MakePoint(127.0276, 37.4979), 4326)::geography
  ) AS distance_meters
FROM member_work_locations mwl
WHERE mwl.user_id = 'user-uuid'
  AND mwl.entity_id = 'org-uuid'
  AND mwl.is_active = true
  AND ST_DWithin(
    mwl.geom::geography,
    ST_SetSRID(ST_MakePoint(127.0276, 37.4979), 4326)::geography,
    mwl.allowed_radius_meters
  )
ORDER BY distance_meters ASC
LIMIT 1;

-- 조직 기본 사업장 반경 내 확인
SELECT 
  wl.id,
  wl.name,
  ST_Distance(
    wl.geom::geography,
    ST_SetSRID(ST_MakePoint(127.0276, 37.4979), 4326)::geography
  ) AS distance_meters
FROM work_locations wl
WHERE wl.entity_id = 'org-uuid'
  AND wl.entity_type = 1
  AND wl.is_active = true
  AND (
    wl.allow_anywhere = true
    OR ST_DWithin(
      wl.geom::geography,
      ST_SetSRID(ST_MakePoint(127.0276, 37.4979), 4326)::geography,
      wl.allowed_radius_meters
    )
  )
ORDER BY distance_meters ASC
LIMIT 1;
```

**PostGIS 사용의 장점:**
* **성능**: GIST 공간 인덱스로 반경 검색이 매우 빠름
* **정확도**: 지구 곡률을 고려한 정확한 거리 계산
* **기능**: 다양한 공간 연산 함수 제공 (ST_DWithin, ST_Distance 등)
* **표준**: OGC 표준 준수

## **6\. 핵심 RLS 정책 (v5.2) \- 위치 관련 RLS 추가**

* **RLS (예: entity\_subscriptions 테이블 조회/수정 권한)**  
  * "오직 해당 엔티티의 OWNER 또는 MANAGER 권한이 있는 사용자만 이 행을 조회할 수 있다."  
  * **SQL (RLS Policy for entity\_subscriptions \- SELECT):**  
    EXISTS (  
      SELECT 1 FROM memberships m  
      WHERE m.user\_id \= auth.uid()  
        AND m.entity\_id \= entity\_subscriptions.entity\_id  
        AND m.entity\_type \= entity\_subscriptions.entity\_type  
        AND (  
          \-- 1\. 조직/센터의 매니저/오너 권한 (예시: ORG\_MANAGER 비트)  
          (m.entity\_type \= 1 AND (m.permissions & 4\) \<\> 0\) OR \-- ORG\_MANAGE\_MEMBERS  
          (m.entity\_type \= 2 AND (m.permissions & 4096\) \<\> 0\) \-- CENTER\_MANAGE\_ORGS  
        )  
    )

  * **참고:** 이 테이블의 INSERT/UPDATE는 RLS가 아닌 service\_role 키를 사용하는 api/webhooks/payment에서만 수행되어야 합니다.  
* **RLS (예: location\_proofs 테이블 조회 권한)**  
  * "1. 본인이 생성했거나, 2\. 증빙이 조직(type=1) 소속이고 내가 그 조직 관리자이거나, 3\. 증빙이 센터(type=2) 소속이고 내가 그 센터 관리자이거나, 4\. 증빙이 조직(type=1) 소속이고 내가 그 조직을 관리하는 센터의 관리자여야 한다."  
  * **SQL (RLS Policy for location\_proofs \- SELECT):**  
    (  
      \-- 1\. 본인이 생성한 증빙인 경우  
      location\_proofs.user\_id \= auth.uid()  
    ) OR (  
      \-- 2\. 증빙이 조직(type=1) 소속이고, 내가 그 조직의 관리자인 경우  
      (  
        location\_proofs.entity\_type \= 1 AND \-- 1 \= ORGANIZATION  
        EXISTS (  
          SELECT 1 FROM memberships m  
          WHERE m.user\_id \= auth.uid()  
            AND m.entity\_id \= location\_proofs.entity\_id  
            AND m.entity\_type \= 1  
            AND (m.permissions & 4\) \<\> 0 \-- 4 \= ORG\_MANAGE\_MEMBERS  
        )  
      )  
    ) OR (  
      \-- 3\. (v4.1 신규) 증빙이 센터(type=2) 소속이고, 내가 그 센터의 관리자인 경우  
      (  
        location\_proofs.entity\_type \= 2 AND \-- 2 \= CENTER  
        EXISTS (  
          SELECT 1 FROM memberships m  
          WHERE m.user\_id \= auth.uid()  
            AND m.entity\_id \= location\_proofs.entity\_id  
            AND m.entity\_type \= 2  
            AND (m.permissions & 4096\) \<\> 0 \-- 4096 \= CENTER\_MANAGE\_ORGS  
        )  
      )  
    ) OR (  
      \-- 4\. 증빙이 조직(type=1) 소속이고, 내가 그 조직을 관리하는 센터의 관리자인 경우  
      (  
        location\_proofs.entity\_type \= 1 AND \-- 1 \= ORGANIZATION  
        EXISTS (  
          SELECT 1  
          FROM memberships m  
          JOIN center\_org\_relationships cor ON cor.center\_id \= m.entity\_id  
          WHERE m.user\_id \= auth.uid()  
            AND m.entity\_type \= 2 \-- 2 \= CENTER  
            AND cor.organization\_id \= location\_proofs.entity\_id  
            AND (m.permissions & 4096\) \<\> 0 \-- 4096 \= CENTER\_MANAGE\_ORGS  
        )  
      )  
    )

  * **SQL (RLS Policy for location\_proofs \- INSERT):**  
    \-- (v4.1) 본인의 증빙은 본인이 삽입할 수 있음 (user\_id가 본인인지 RLS가 강제)  
    (  
      location\_proofs.user\_id \= auth.uid()  
    )

## **7\. 인증 및 접근 제어 (Auth Flow) \- v5.6 핵심 수정**

**v5.6 주요 변경사항**: JWT 기반 통합 접근 제어 전략 도입으로 미들웨어에서 DB 조회 없이 권한/구독 체크 수행.

### **7-1. JWT 기반 멤버십 구조 (v5.6 신규)**

JWT의 `app_metadata`에 구독 상태와 권한 정보를 통합하여 저장합니다.

**JWT app_metadata 구조:**
```json
{
  "app_metadata": {
    "memberships": {
      "org-uuid-1": [1, "1f"],       // [Status, Permissions(Hex)]
      "center-uuid-A": [2, "400"],   // [Status, Permissions(Hex)]
      "org-uuid-2": [1, "5"]         // [Status, Permissions(Hex)]
    }
  }
}
```

* **Index 0 (Status):** 구독 상태 코드 (1: Active, 2: Past Due, 3: Suspended, 4: Canceled)
* **Index 1 (Permissions):** 권한 비트필드 값을 **16진수 문자열(Hex String)**로 변환하여 저장
  * *이유:* BigInt(64bit)는 JSON 숫자로 표현 시 정밀도 손실 위험이 있으며, 10진수 문자열보다 16진수가 더 짧아 용량을 절약함.

### **7-2. Database Hook 구현 (v5.6 신규)**

JWT 생성 시 memberships 정보를 자동으로 주입하는 Hook 함수를 구현합니다.

**마이그레이션 파일 예시:**
```sql
-- [Hook] 통합 멤버십 정보 주입
CREATE OR REPLACE FUNCTION public.custom_access_token_hook(event jsonb)
RETURNS jsonb LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
  claims jsonb;
  user_id uuid;
  membership_map jsonb;
BEGIN
  user_id := (event->>'user_id')::uuid;

  -- 1. 전체 멤버십 조회 (50개 제한 보장됨)
  -- 권한(bigint)를 to_hex()로 변환하여 용량 절약 및 정밀도 보장
  SELECT jsonb_object_agg(
    m.entity_id::text,
    json_build_array(
      COALESCE(es.status, 1),       -- Index 0: Status
      to_hex(m.permissions)         -- Index 1: Permissions (Hex)
    )
  )
  INTO membership_map
  FROM public.memberships m
  LEFT JOIN public.entity_subscriptions es
    ON m.entity_id = es.entity_id AND m.entity_type = es.entity_type
  WHERE m.user_id = user_id;

  -- 2. JWT 주입
  claims := event->'claims';
  
  IF jsonb_typeof(claims->'app_metadata') IS NULL THEN
    claims := jsonb_set(claims, '{app_metadata}', '{}');
  END IF;

  -- 'memberships' 필드에 주입
  claims := jsonb_set(claims, '{app_metadata,memberships}', COALESCE(membership_map, '{}'));

  event := jsonb_set(event, '{claims}', claims);
  RETURN event;
END;
$$;
```

**Supabase Dashboard 설정:**
* Authentication > Hooks > Access Token Hook에 `custom_access_token_hook` 함수 등록

### **7-3. 미들웨어 로직 (v5.6 수정)**

미들웨어는 이제 JWT에서 memberships 정보를 파싱하여 권한과 구독 상태를 동시에 체크합니다.

**필수 검사 로직:**
1. **조직 관리 페이지:** ORG_VIEW (1) 권한 비트가 켜져 있는지 확인
2. **센터 관리 페이지:** CENTER_VIEW (1024) 권한 비트가 켜져 있는지 확인
3. **구독 상태 체크:** Status가 ACTIVE(1)인지 확인

**middleware.ts 예시:**
```typescript
import { NextResponse, type NextRequest } from 'next/server';
import { createServerClient } from '@supabase/ssr';

// 권한 비트 상수 (BigInt) - lib/permissions.ts와 동기화
const PERM_BITS = {
  ORG_VIEW: BigInt(1),        // 1 << 0
  CENTER_VIEW: BigInt(1024),  // 1 << 10
};

export async function middleware(request: NextRequest) {
  // ... (Supabase 클라이언트 초기화) ...
  const { data: { user } } = await supabase.auth.getUser();

  if (user) {
    const pathParts = request.nextUrl.pathname.split('/');
    // memberships 구조: { [entityId]: [status(number), permHex(string)] }
    const memberships = user.app_metadata?.memberships as 
      Record<string, [number, string]> | undefined;

    // [Tier 2] 조직 관리 경로 체크
    if (pathParts[1] === 'org-management' && pathParts[2]) {
      const entityId = pathParts[2];
      const data = memberships?.[entityId];

      // 1. 멤버십 존재 여부 확인
      if (!data) {
        return NextResponse.redirect(new URL('/dashboard', request.url));
      }

      const [status, permHex] = data;

      // 2. 권한(Permission) 체크 (RBAC)
      // Hex String -> BigInt 변환
      const permissions = BigInt(`0x${permHex}`);
      
      // ORG_VIEW 권한이 없으면 접근 차단
      if ((permissions & PERM_BITS.ORG_VIEW) === 0n) {
        return NextResponse.redirect(
          new URL('/dashboard?error=forbidden', request.url)
        );
      }

      // 3. 구독(Subscription) 체크
      if (status !== 1) { // ACTIVE
        if (!request.nextUrl.pathname.includes('/billing')) {
          return NextResponse.redirect(
            new URL(`/org-management/${entityId}/billing`, request.url)
          );
        }
      }
    }
    
    // [Tier 2] 센터 관리 경로 체크 (동일 로직)
    if (pathParts[1] === 'center-management' && pathParts[2]) {
      const entityId = pathParts[2];
      const data = memberships?.[entityId];

      if (!data) {
        return NextResponse.redirect(new URL('/dashboard', request.url));
      }

      const [status, permHex] = data;
      const permissions = BigInt(`0x${permHex}`);
      
      if ((permissions & PERM_BITS.CENTER_VIEW) === 0n) {
        return NextResponse.redirect(
          new URL('/dashboard?error=forbidden', request.url)
        );
      }

      if (status !== 1) {
        if (!request.nextUrl.pathname.includes('/billing')) {
          return NextResponse.redirect(
            new URL(`/center-management/${entityId}/billing`, request.url)
          );
        }
      }
    }

    // [Tier 3] 앱 매니저 경로 체크
    if (pathParts[1] === 'app-manager') {
      // profiles.permissions는 JWT에 포함되지 않으므로 DB 조회 필요
      // 또는 별도의 app_metadata 필드에 저장
      const { data: profile } = await supabase
        .from('profiles')
        .select('permissions')
        .eq('id', user.id)
        .single();
      
      if (!profile || (BigInt(profile.permissions) & PERMISSIONS.IS_APP_MANAGER) === 0n) {
        return NextResponse.redirect(new URL('/dashboard', request.url));
      }
    }
  }

  return supabaseResponse;
}
```

### **7-4. PermissionsBitField 확장 (v5.6 신규)**

export class PermissionsBitField {
  // ... 기존 구현 ...

   * JWT Hex String에서 인스턴스 생성 헬퍼

### **7-5. 기대 효과 (v5.6)**

1. **Tier 2 보안 강화:** 미들웨어 단계에서 악의적인 URL 접근(권한 없는 사용자가 /settings 접근 등)을 원천 차단합니다.
2. **완벽한 Zero DB Latency:** 페이지 이동 시 DB를 전혀 조회하지 않으므로, 관리자 페이지의 로딩 속도가 일반 페이지(SPA)급으로 향상됩니다.
3. **데이터 일관성:** 구독 상태와 권한 정보가 하나의 스냅샷(JWT)으로 관리되어 동기화 문제가 감소합니다.

### **7-6. 주의사항 (v5.6)**

1. **JWT 크기 제한:** JWT는 4KB 제한이 있으므로, memberships가 50개를 초과하지 않도록 제한 필요
2. **데이터 일관성:** JWT는 캐시된 데이터이므로, 권한/구독 변경 시 즉시 반영되지 않을 수 있음
   * 해결책: 권한/구독 변경 시 관련 사용자들의 세션 갱신 필요
3. **Webhook 연동:** 결제 웹훅에서 구독 상태 변경 시 사용자 세션 갱신 로직 추가 필요

**\[1단계 v5.6 확정 및 2단계 진행\]**

SaaS의 핵심 기능과 비즈니스 모델(BM)이 모두 정의된 **v5.6** 계획입니다.

**v5.6 주요 변경사항 (JWT 기반 통합 접근 제어):**
* **JWT 기반 멤버십 구조**: `app_metadata.memberships`에 구독 상태와 권한 정보를 통합 저장
* **Database Hook**: `custom_access_token_hook` 함수로 JWT 생성 시 memberships 정보 자동 주입
* **Zero DB Latency**: 미들웨어에서 DB 조회 없이 JWT 파싱으로 권한/구독 체크
* **PermissionsBitField.fromHex()**: JWT Hex String에서 권한 객체 생성 헬퍼 메서드 추가
* **성능 최적화**: 관리자 페이지 로딩 속도가 일반 페이지(SPA)급으로 향상

**v5.2 주요 변경사항 (PostGIS 기반 위치 관리):**
* **PostGIS 확장 사용**: 모든 위치 데이터는 `GEOMETRY(Point, 4326)` 타입 사용
* **조직 기본 사업장**: `work_locations` 테이블로 조직/센터별 n개 사업장 관리
* **직원별 근무지**: `member_work_locations` 테이블로 직원별 n개 근무지 관리
* **위치 검증 로직**: 직원 근무지 → 조직 사업장 → 아무데서나 허용 순서로 검증
* **공간 인덱스**: GIST 인덱스로 반경 검색 성능 최적화

**v5.1 주요 변경사항 (3-Tier 아키텍처 모델 반영):**
* **Tier 1 (일반 사용자)**: 클라이언트 직접 접근 - 위치 증빙 생성 등 일반 사용자 작업
